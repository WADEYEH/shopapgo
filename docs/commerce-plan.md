## 0. 一页摘要

**目标**：美国顾客在 www.shopapgo.com 看完内容就能直接下单付款，由 Amazon 仓库（MCF）出货，售后在我们自己的后台处理。

**现况**：

- 功能大致都做出来了，但分散在两个 repo、三个网站：
  - 品牌站 `www.shopapgo.com/us`（shopapgo repo）
  - landing 线上店 `store.shopapgo.com`（landing repo 的代码，目前唯一能真实付款的地方）
  - 测试店 `staging.shopapgo.com`（两个 repo 都会部署到这里，互相覆盖）
- 后端功能两边互补：shopapgo 有退款、付款失败处理、可重试的邮件和出货检查；landing 有 Meta 广告追踪、产品页和正式环境设定。重复的部分在前台：Pixel、产品展示、导航、进度文件。
- landing 线上店的结账开着，但没有设定寄信，也没接上 Amazon 出货。线上设定跟任何 repo 都对不上，是从某台电脑直接部署的。

**要做的事**（约 3.5 周工作量，见第 6 章）：

- 阶段 0：建立 landing 的同步点，把正式环境的现况完整记下来
- 设计阶段：列出所有情境（含取消、退款、退货、出错等例外），确定模块划分，每个模块写设计规格。你审核后才开始写新代码
- 阶段 1：把 landing 的东西并进 shopapgo，只留一个 repo
- 阶段 2：产品页、购物车、结账、政策页搬进品牌站，变成同一个网站，并套用新的运费、配送范围和退货规则
- 阶段 3：后台改成每人用 Google 帐号登录；接上 Amazon 出货、寄信和通知
- 阶段 4：在 staging 全部验收，再把 www.shopapgo.com 切过去，store.shopapgo.com 转址
- 阶段 5：封存 landing，清理旧设定

**需要你或外部提供的**（见第 8 章）：销售税要问会计师；GTM 留哪一套；运费金额最后确认；政策文字要法务审核。

### 3.2 系统组成

```
顾客浏览器
   │  www.shopapgo.com
   ▼
Cloudflare Worker「apgo-us-store」（沿用现有的正式环境资源，一个部署单位）
   ├─ 静态页面：Next.js 汇出的品牌站和商店页面
   ├─ /api/*：报价、建立订单、Airwallex webhook、Resend webhook、订单查询
   ├─ admin.shopapgo.com：后台页面与 API（Cloudflare Access 保护）
   └─ 排程（每 15 分钟）：MCF 追踪同步、邮件重试、Meta 事件补送
        │
        ├── D1 数据库：订单、付款、退款、出货、邮件、广告归因
        ├── Airwallex：收款、退款
        ├── amazon-spapi-mcp Worker → Amazon MCF：建单、追踪、库存
        ├── Resend：顾客邮件、团队通知
        └── Meta Conversions API：服务器端广告事件
浏览器端另外载入：GTM → GA4、Meta Pixel
```

**为什么把整个网站放进一个 Worker，而不是继续用 Pages**：

- 后端本来就要用 Worker（排程、D1、webhook）。静态页面也放进同一个 Worker，就是一次部署、一份设定，不会再出现页面和后端版本对不上的情况。
- 沿用现有的正式环境资源（Worker `apgo-us-store` 和正式数据库）。这些是公司在 Cloudflare 上的资源，不属于哪个 repo；现在跑的是 landing 的代码，切换后换成 shopapgo 的代码。这样 store 和 admin 的网域绑定、数据库绑定都不用动，已有的订单也不用搬；出问题时可以直接回到切换前的版本。
- 只有 `/api/*`、后台和 Apple Pay 验证文件会进 Worker 代码，其他静态页面直接由 Cloudflare 提供，速度和成本跟 Pages 一样。Cloudflare 也在引导 Pages 专案改用这种方式。

## 4. 模块设计

每个模块按「目的 → 现况 → 做法 → 规则 → 验收标准」写。

> 以下是初版的 13 个模块。10/5 已确认改为 12 个（D20，见 `docs/design/scenarios.md` 第 3 节）：拆出「订单核心」、新增「售后」、价格运费税统一归「商品与价格」。各模块的设计规格写完后，本章会改成模块总览，细节以规格为准。

### 4.1 内容与商品资料

**目的**：所有地方共用同一份商品资料，避免文案不一致。

**现况**：品牌站首页和指南（经过 FTC 审核的文案）、landing 产品页（`product-data.js`）、v3 页面各有一份。

**做法**：

- 建立 `lib/us/catalog/`，每个商品一份资料：网址名称、SKU、对应的 Amazon seller SKU 与 ASIN、名称、容量、价格、图片、卖点、FAQ、可宣称的内容。
- 产品页、首页卡片、指南里的产品卡片、结构化资料、后端价格表，全部从这里读取。
- 组合包（D16）用同一种资料格式，多一个栏位 `components: [{ sku, qty }]`，价格另外订；出货时拆成单品送给 MCF。
- 文案规则：只能用 claim ledger（landing `docs/v2/claim-ledger.md`，合并后搬到 `docs/content/`）里核准过的说法。运费、退货、送达时间只能引用政策页的数字，文案里不另外写。

**验收标准**：

- 改一次价格，产品页、购物车、结账、结构化资料、后端金额全部一致（有测试）。
- 全站搜不到「TO CONFIRM」或未核准的承诺字样（有测试）。

### 4.2 产品页与 SEO

**做法**：

- 两个产品页加一个总览页，用品牌站同一套版型。
- 结构化资料：`Product` + `Offer`（价格、库存状态）+ `OfferShippingDetails`（运费、配送范围、处理与运送天数，跟运费政策一致）+ `MerchantReturnPolicy`（30 天、未开封、退货运费由顾客付）。这样产品在 Google 搜索结果中有机会显示价格和运费。
- sitemap 加入产品页和总览页；购物车、结账、订单页设为 `noindex`。
- 首页 5 个按钮改连产品页或直接加入购物车；指南里的产品卡片改连产品页。
- store.shopapgo.com 的旧网址逐一 301 到新网址（例如 `/products/d204.html` → `/us/products/colored-glaze`）。

**验收标准**：

- 用 Google Rich Results Test 检查两个产品页，能解析出 Product，零错误。
- sitemap 包含所有可收录的页面（沿用现有的 sitemap 漂移测试）。
- 旧网址逐一 301 到正确的新网址（有测试清单）。

### 4.3 购物车

**做法**：

- 改写成 Next.js 前端元件。购物车内容存在浏览器（localStorage），不需要登录。
- 金额一律由后端计算：`POST /api/cart/quote` 回传品项、小计、运费、税和总额，前端只负责显示。
- 每个品项最多 10 件（沿用 `maxQtyPerLine`）。
- 缺货时（见 4.7）该商品不能加入购物车或结账。

**验收标准**：

- 窜改前端的价格，不会影响结账金额（有测试）。
- 数量上限、空购物车、商品下架等情况都有对应画面。

### 4.4 结账、地址与运费

**规则**：

- 运费：每张订单 **$7.99**（D12，金额待确认），只有标准配送。
- 送达说法：「从美国仓库出货，大多 3–5 个工作日送达」。不写保证日期；10/15–1/14 旺季加注可能延迟。
- 配送范围：48 州加 DC。不送阿拉斯加、夏威夷、波多黎各和其他领地、军邮（APO/FPO/DPO）、邮政信箱（PO Box）。地址表单只列出可送的州，后端再检查一次。
- 税：等会计师意见（O1）。代码里保留一个可替换的计税步骤，目前回传 $0，并在后台标示「未计税」。
- 付款前显示总额（含运费和税），实际收款金额以后端为准。

**做法**：

- 沿用后端的 `validateCheckout` 和 `quote`，新增：州的白名单、PO Box 与军邮判断、电话栏位，运费改成设定值。
- 接地址验证服务（D18）：结账时检查地址，建议修正；无法投递或缺门牌、楼层号的地址，要顾客修正或确认后才能下单。用哪一家服务，在购物车与结账模块的设计规格里比较。
- 运费金额放在设定（`PRICING_JSON`）里，改金额不用改代码。
- 拿掉「加急」选项。以后要开再定价（成本约 $12–15）。

**验收标准**：

- 阿拉斯加、夏威夷、PO Box、APO 地址会被拒绝，并有清楚提示（有测试）。
- 任何组合的订单，运费都是 $7.99（有测试）。
- 页面上的送达说法和政策页一致（测试比对文字）。

### 4.5 付款（Airwallex）

**现况**：两边都有 Airwallex 串接；shopapgo 多了付款失败纪录与重试。正式环境用的是 Airwallex 正式帐户。

**做法**：

- 流程：建立订单（待付款）→ 建立 PaymentIntent（以订单编号作为 `request_id`，防止重复）→ 前端用 Airwallex 卡片栏位确认付款 → webhook `payment_intent.succeeded` → 订单改为已付款 → 触发后续动作（确认信、团队通知、Meta Purchase、出货）。
- webhook 一律验证签章（HMAC）；同一个事件只处理一次（`webhook_events` 表）。
- 付款失败（`payment_attempt.*`）会记录原因，顾客可以用同一张订单重试。
- Apple Pay / Google Pay 也走 Airwallex。www.shopapgo.com 要在 Airwallex 重新登记网域，Apple Pay 的网域验证文件由 Worker 提供。上线初期可以先关，等卡片流程稳定再开。
- PayPal（D21）：沿用 landing 已上线的 Orders v2 实作。要补上背景通知设定、PayPal 地址检查、退款、拒付和对帐（情境 D15–D19）。

**验收标准**：

- sandbox 里，付款成功、失败（用官方测试卡）、重试、重复的 webhook、签章错误，结果都正确（沿用现有测试）。
- 切换到正式环境后，完整走通一笔真实小额付款加退款（由你或同事操作）。

### 4.6 订单与后台

**订单状态**：`pending`（待付款）→ `paid`（已付款）→ 出货状态（未出货 / 已送 Amazon / 已出货）。另外有 `review`（需人工确认）和 `cancelled`。退款另外记录（部分或全额）；有退款登记时，未出货的订单会自动冻结。

**后台功能**（沿用 shopapgo 版本）：订单列表与筛选；订单详情（品项、地址、付款、退款、邮件、操作纪录）；送 Amazon 出货；同步追踪；手动标记已出货；重寄邮件；同步退款。

**登录方式（D15）**：

- 改用 **Cloudflare Access**：你和 1–3 位同事用公司的 Google 帐号登录（50 人以内免费）。
- Worker 读取 Access 提供的使用者身份，写进操作纪录：谁、什么时候、做了什么。
- 原本共用的 `ADMIN_TOKEN` 只留给自动化脚本用，或直接移除。
- 以后如果有外包客服，再加一个「只能查看、不能退款或出货」的角色。

**验收标准**：

- 没登录、或不在名单里的人打不开后台（有测试，也要实测）。
- 每个操作都记录到操作人。
- 后台只在 admin 网域能用，www 上的 `/admin` 回传 404（沿用现有测试）。

### 4.7 出货（Amazon MCF）

**现况**：shopapgo 版本有完整的 MCF 流程（送单、防重复、追踪同步、取消、只读连线检查），在 staging 只做过只读检查。正式环境还没接上（缺 `OUTBOUND_INTERNAL_TOKEN` 等设定）。真实出货从来没测过（D6）。

**做法**：

- 透过既有的 `amazon-spapi-mcp` Worker 呼叫 Amazon。
- **付款后自动送单**（D19）：地址已在结账时由验证服务检查（D18），付款成功后系统自动送 Amazon（`MCF_AUTO_SUBMIT`），失败时通知团队。
- 追踪同步：排程每 15 分钟同步一次 MCF 状态；出货后寄出货通知（含追踪号）。
- 退款冻结：已登记退款的订单不会被送出。
- 库存：结账前用 MCF 预览或库存查询确认可以出货；库存不足时，产品页显示缺货。库存和 Amazon 通路共用，网站订单会用掉同一批 FBA 库存。
- 失败处理：送单失败时记录原因并通知团队；后台可以重送或改为人工处理。
- 组合包：送单时拆成单品 SKU。

**送单验证**（D26）：不做真实出货测试。上线前在正式环境建一张暂缓出货（Hold）的测试单，Amazon 接受后马上取消；之后每次送单都自动读回 Amazon 的出货单，比对商品、数量、地址，不一致就通知团队。

**验收标准**：

- staging：用假的 MCF 服务跑通送单、重复送单被挡、追踪同步、出货信、退款冻结（沿用现有测试）。
- 正式环境：两个 SKU 的只读连线检查都通过；Hold 测试单建立成功并取消；送单后自动比对机制运作（D26）。

### 4.8 退款与退货

**规则（D13）**：

- 收到商品 30 天内、未开封，可以退货。
- 改变心意：顾客付退货运费。瑕疵、寄错、运送损坏：由我们付运费，补寄或退款。
- 退款退回原付款方式；收到退货并检查后才处理。
- 已经送给 Amazon 的订单不保证能取消。能取消就取消，不能取消就走退货流程。

**做法**：

- 初期在 Airwallex 后台发起退款。系统透过 webhook 自动记录、冻结出货，并通知顾客和团队（shopapgo 版已经做好）。
- 之后可以在后台直接按「退款」（要有 Access 角色控管）。
- 退货收件：用 Amazon MCF 的退货流程收回仓库，或请顾客寄到指定地址。谁负责、寄到哪里，待决（O5）。

**验收标准**：

- sandbox 里，部分退款、全额退款、退款失败，各自的纪录、冻结和通知都正确（沿用现有测试）。
- 退货政策页的文字和以上规则一致，并经过法务确认。

### 4.9 顾客通知与团队通知

**信件种类**：订单确认、出货通知（含追踪号）、退款通知、退款失败（寄给团队）、新订单通知（寄给团队）。

**做法**：

- 用 Resend 寄信，采用「先写进数据库、再寄出、失败就重试」的方式（shopapgo 版），不会因为一时失败就漏信。
- Resend 回传的送达和退信事件，先验证签章再记录；退信或被投诉的地址会自动停寄。
- 寄件人：目前核准的是 `APGO <orders@apgo.tw>`，回复寄到 `services@apgo.com.tw`。建议之后改用 `shopapgo.com` 网域寄件，跟网站一致（要在 Cloudflare 加 DNS 验证记录），见 O8。
- 团队通知寄到 wadeyeh@apgo.com.tw（D7），之后可以加同事。

**验收标准**：

- staging：五种信件都能产生并寄到测试信箱；模拟寄送失败后，会重试成功（沿用现有测试）。
- 正式环境：切换当天用真实订单收到确认信和团队通知。

### 4.10 追踪与分析

**做法**：

- **GTM / GA4 只留一套**（O2）。
- **Meta Pixel 只留一份代码**，放在 Next.js 共用元件里，只在 www.shopapgo.com 正式环境启动。
- 事件对照：

| 时机 | GA4（经 GTM） | Meta Pixel（浏览器） | Meta CAPI（服务器） |
|---|---|---|---|
| 看产品页 | `view_item` | ViewContent | — |
| 加入购物车 | `add_to_cart` | AddToCart | — |
| 进入结账 | `begin_checkout` | InitiateCheckout | InitiateCheckout（`ic_<订单编号>`） |
| 付款成功 | `purchase` | Purchase | Purchase（`purchase_<订单编号>`） |

- 浏览器和服务器的 Meta 事件用同一个 event ID，让 Meta 自动去重（landing 已经做好，直接并入）。
- 移除品牌站的 `AmazonClick` 和 `amazon_referral_click`，已经用不到。
- 既有的内容事件（`scroll_depth`、`faq_expand` 等）保留。
- `META_TEST_EVENT_CODE` 只在测试时设定，确认用途后从正式环境移除。

**验收标准**：

- 在 GTM 预览和 Meta 测试事件工具里，四个时机的事件都会出现，参数（金额、币别、商品）正确。
- Purchase 在 Meta 只算一次（浏览器和服务器去重成功）。
- staging 和本机不会送出任何事件。

- 在 Next.js 里做：商品总览、两个产品页、购物车、结账、订单页、政策页、联络页（4.1–4.4、4.11）。购物车和结账沿用现有逻辑，改写成 Next.js 元件；端到端测试改成测新页面。
- 套用新规则：运费 $7.99、48 州加 DC、新退货政策、拿掉加急。
- 首页和指南的按钮改连商品；统一 Meta Pixel；加上 GA4 电商事件和产品结构化资料。
- Worker 改成同时提供 Next.js 静态页面（先在 staging 上做）。

**完成条件**：staging 上是完整的单一网站；端到端测试通过；手机、平板、桌面的画面检查通过。

### 阶段 3：后台与营运（约 2–4 天）

- 后台改用 Cloudflare Access 登录（4.6）。
- 设定正式环境的 MCF 连线、Resend、团队通知和错误告警（先在 staging 验证）。
- 组合包（如果届时已经确定组合）。

**完成条件**：在 staging 走完一轮：付款 → 送单（假服务）→ 出货信 → 退款 → 冻结 → 通知。

### 阶段 4：验收与切换（约 2–3 天，另加观察 48 小时）

- 跑完第 9 章的上线验收。
- 切换步骤（由我执行，你在线上待命）：
  1. 备份正式数据库，套用迁移。迁移只新增资料表，不影响旧版还在运作的店。
  2. 把 shopapgo 的新版部署到正式环境的 Worker `apgo-us-store`，取代 landing 的代码（沿用正式数据库和 Airwallex 正式帐户）。store 和 admin 的网域本来就绑在这个 Worker 上：store 的网址改为 301 转到 www，webhook 路径照常处理。
  3. 把 `www.shopapgo.com` 从 Pages 移到这个 Worker（先在 staging 网域演练过）。
  4. 在 Airwallex 和 Resend 把 webhook 网址改成 www；在 Airwallex 登记 www 网域（Apple Pay 需要）。
  5. 冒烟测试：页面、购物车、后台、邮件、Pixel/GA4。送单验证（D26）：在正式环境建一张 Hold 出货单，确认 Amazon 接受后取消。
  6. 观察 48 小时。Search Console 是用网域验证的，不受影响，重新提交 sitemap 即可。
- 回退方案：Worker 可以直接回到切换前的版本；Pages 专案保留两周，www 可以在几分钟内改回 Pages。数据库只新增了资料表，旧版可以照常读写。

**完成条件**：正式环境全部由新版服务；48 小时内没有未处理的错误。

### 阶段 5：收尾（约 1 天）

- landing repo 改为封存（只读）。之后再决定是否删除，删除由你操作。
- 稳定两周后删除 Pages 专案（由你操作）。
- 删掉过时的文件和设定：`vercel.json`、旧进度文件、不用的密钥。
- 执行 GTM/GA4 的决定（O2）。

**总计**：约 3.5 周工作量（含设计阶段）。实际时程取决于待决事项（特别是税和法务）什么时候有答案；如果税需要代收，要在切换前做好。

## 10. 工作方式（避免再各做各的）

- shopapgo 是唯一的 repo；landing 合并后封存。
- 合并完成前，landing 会继续开发（D22）：请 Cursor 开工前读本企划和设计规格，PR 描述写上对应的情境编号，不做跟决定冲突的东西。
- 开始任何工作前，先读这份企划。只做企划里的项目；要做企划外的事，先更新企划。
- 新功能先有设计规格（含对应的情境和验收测试），再写代码。
- 一次由一个 agent 负责一个阶段。交接时更新本文件第 11 章的进度，不另外写交接文件。
- 所有改动都走 PR 进 `main`；正式部署只能由 CI 执行，并经过你核准。
- 正式环境的设定变更（含密钥）先记录在 `docs/ops/production-config.md`。

## 附录 A：名词解释

| 名词 | 意思 |
|---|---|
| MCF | Amazon Multi-Channel Fulfillment：用放在 Amazon 仓库的库存，帮我们网站的订单出货 |
| FBA | Fulfillment by Amazon：库存放在 Amazon 仓库，Amazon 上的订单由 Amazon 出货 |
| Airwallex | 收款服务，处理信用卡、Apple Pay、Google Pay 和退款 |
| Worker | Cloudflare 上执行代码的地方；我们的网站和后端会放在同一个 Worker |
| D1 | Cloudflare 的数据库，用来存订单等资料 |
| webhook | 外部服务（Airwallex、Resend）主动通知我们「付款成功了」「信寄到了」的机制 |
| staging | 测试用的网站，跟正式站同一套代码，但用测试帐户 |
| CI | 每次改代码时，自动跑测试、自动部署的流程（GitHub Actions） |
| GTM / GA4 | Google 的标签管理工具 / 网站分析工具 |
| Meta Pixel / CAPI | Meta 广告追踪。Pixel 在浏览器端，CAPI 在服务器端，两个一起用能让广告成效算得更准 |
| Cloudflare Access | 让后台只有指定的 Google 帐号能登录的服务 |
| PaymentIntent | Airwallex 里「一笔付款」的物件 |
| 301 | 永久转址：旧网址自动导到新网址，搜索引擎也会跟着更新 |
