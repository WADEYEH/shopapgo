## 1. 结论

- **landing 有、shopapgo 没有**：Meta 追踪、产品页、PayPal、Airwallex Pay、后台 email＋密码登录、结账资料保留、正式环境设定。合并时要带进来。
- **shopapgo 有、landing 没有**：退款处理、付款失败纪录、可追踪的寄信与停寄名单、出货的退款冻结与只读检查。合并时要保留。
- **两边都没有**：售后整块、拒付、对帐、配送范围、地址验证、电话、逾时取消、冷静期、个人登录等。合并后照情境清单补。
- **PayPal 带来 8 个新情境**（D13–D20），其中退款、拒付、背景通知、地址检查都还没做。

## 5. PayPal 带来的新情境

| 编号 | 情境 | 建议处理 | landing 现况 | 模块 |
|---|---|---|---|---|

## 6. 正式店现在就有的风险（不等合并）

| 风险 | 建议 |
|---|---|
| PayPal 背景通知没设定（缺 `PAYPAL_WEBHOOK_ID`） | 现在就补：在 PayPal 开发者后台建立 webhook，网址 `https://store.shopapgo.com/api/webhooks/paypal`，再把 webhook ID 设成正式环境密钥。PayPal 后台要你登录操作 |
| 任何付款方式的退款都不会被系统记录（landing 没有退款处理） | 过渡期规则：在 Airwallex 或 PayPal 退款后，记得去后台查看那张订单，不要再出货 |
| PayPal 订单的地址没检查（D16） | 过渡期出货本来就是人工在 Seller Central 建单，建单的人顺便确认地址在 48 州加 DC、不是 PO Box |
| 不寄确认信、不通知新订单、没接 Amazon 出货 | 同企划第 7 章 |
| 后台是全员共用的 email＋密码 | 同上，最终改为个人登录 |

## 7. 之后怎么同步

**10/6 更新**：决定留 shopapgo，landing 不再修改，也不再部署（D37）。同步点 1 就是最后一次合并，以下步骤只在 landing 意外又有改动时才需要。

1. **每次合并前**：从上一个同步点开始，只检查新增的改动，把结果加进本文件（新增一节「同步点 2」），并更新情境清单。
2. **合并方式**：第一次合并时保留 landing 的 git 历史，之后 landing 的新改动可以一批一批增量合进来，不必每次重新处理全部冲突。
3. **请 Cursor 照同一套企划做**：shopapgo 的 `claude/commerce-plan` 分支是公开的，Cursor 读得到。建议请它开工前先读企划和规格，PR 描述写上对应的情境编号，不要做跟决定冲突的东西（例如后台登录方式、配送范围）。这样每次合并要处理的冲突会少很多。
